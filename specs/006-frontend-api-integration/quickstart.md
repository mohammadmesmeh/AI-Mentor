# Quickstart: Validating Frontend API Integration

How to prove this feature works end-to-end once implemented. This is a
validation runbook, not an implementation guide — see `data-model.md` and
`contracts/api-client.md` for the shapes/endpoints involved, and `tasks.md`
(generated by `/speckit-tasks`) for the implementation breakdown.

## Prerequisites

- Backend running locally and reachable at the contract's local base URL
  (`http://localhost:8000/api/v1`). From `Backend/`:
  ```
  docker compose run --rm --no-deps setup
  docker compose run --rm --no-deps setup php artisan key:generate --show
  docker compose up -d
  docker compose exec app php artisan migrate:status   # confirm migrations applied
  ```
  See `Backend/README.md` for full setup detail (env vars, first-run steps).
- Backend CORS allows the frontend origin: `CORS_ALLOWED_ORIGINS=http://localhost:3000`
  (`API_CONTRACT.md` §19).
- Frontend env var set (new for this feature):
  ```
  NEXT_PUBLIC_API_BASE_URL=http://localhost:8000/api/v1
  ```
- Frontend dependencies installed and dev server running: `npm run dev`
  (from `my-app/`).
- Test tooling installed per `research.md` §1 (Vitest, React Testing Library,
  MSW, Playwright) before running the automated scenarios below.

## Automated validation

```
npm run test           # Vitest unit/component/integration suite (MSW-mocked API)
npm run test:e2e        # Playwright smoke suite (real local backend)
```

(Exact script names are defined when the test tooling is wired up as part of
implementation — these are the expected commands per `research.md` §1.)

Expect: all unit/component tests pass against MSW handlers that mirror
`API_CONTRACT.md`'s exact response shapes (success and error envelopes); the
Playwright suite passes against the real local backend for the one
end-to-end scenario below.

## Manual / end-to-end validation scenarios

Each maps directly to a spec User Story's acceptance scenarios — run them in
order, since US2 depends on US1 and US3 depends on US2.

### Scenario 1 — Account access (spec User Story 1)

1. Register a new account with a fresh email. **Expect**: signed in
   immediately, landed on onboarding, default preferences already applied
   (verify via `GET /me/preferences` in devtools network tab: `en` /
   `both` / `UTC`).
2. Sign out. **Expect**: local session state clears immediately (verify no
   further authenticated requests succeed without signing in again).
3. Sign back in with the same credentials. **Expect**: routed based on
   current onboarding state, not always the same screen.
4. Sign in with a wrong password. **Expect**: a single generic invalid-
   credentials message — indistinguishable from "no such account" (FR-002).
5. Reload the page after signing in. **Expect**: signed out (in-memory-only
   session per spec Assumptions) — this is correct behavior for this
   iteration, not a bug.

### Scenario 2 — Onboarding completion (spec User Story 2)

1. As a signed-in user with incomplete onboarding, confirm the UI shows
   exactly the fields `GET /me/onboarding-status` reports as missing.
2. Save preferences, then save a learning profile (all five required
   fields). **Expect**: after the second save, onboarding status flips to
   `completed: true` without a page reload, and roadmap generation becomes
   available.
3. Save the learning profile again with different values. **Expect**: a full
   replace (`PUT`) — previous values are gone, not merged (FR-010).
4. Attempt to trigger roadmap generation before onboarding is complete (e.g.
   via direct action if the UI path is guarded). **Expect**: blocked, with
   the user directed to what's missing (FR-011).

### Scenario 3 — Roadmap generation and viewing (spec User Story 3)

1. As a user with completed onboarding, request a roadmap. **Expect**: an
   in-progress UI state appears immediately (`202`).
2. Watch the network tab during polling. **Expect**: first poll around 1s,
   later polls backing off toward 2-3s (`research.md` §4), and polling stops
   the instant a terminal status is returned (FR-014).
3. On `succeeded`, **expect**: automatic navigation to the roadmap, stages
   and tasks rendered in `position` order, task action controls visibly
   disabled (no complete/skip affordance — FR-017).
4. Click "Generate roadmap" twice quickly (or trigger a retry after
   simulating a network timeout). **Expect**: exactly one generation job runs
   — verify via the backend that only one `roadmap-generation-requests` row
   was created for that attempt (FR-012, SC-005).
5. Force a generation failure (or use a backend test fixture that produces
   one). **Expect**: a specific, recognizable explanation for a known
   failure reason, and a retry action that uses a **new** idempotency key,
   not the failed one (FR-023, FR-016... FR-012 for the new-key part).

## Sign-off

This feature is validated when all three scenarios above pass manually
against a real local backend, the Playwright smoke test automates Scenario 1
→ 2 → 3 end-to-end, and the Vitest suite covers the refresh-serialization,
idempotency-replay, and error-mapping edge cases from `spec.md`'s Edge Cases
section without needing a live backend (MSW-mocked).
